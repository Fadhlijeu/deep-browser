Gua sudah membaca repository [Fadhlijeu/deep-browser](https://github.com/Fadhlijeu/deep-browser), terutama struktur agent, Chrome Extension, `sidepanelStore`, state machine, sistem verifikasi, Safe Mode, dan bridge Python. Gua juga membandingkan implementasinya dengan dokumentasi arsitektur yang ada.

**Penilaian utama gua: fondasi proyeknya sudah cukup lengkap, tetapi prioritas berikutnya seharusnya konsistensi eksekusi agent, verifikasi hasil, pemisahan runtime, dan keamanan—bukan menambah banyak fitur baru dulu.**

Repository ini memang sudah punya komponen yang tepat: Browser Use sebagai core desktop, extension dengan agent runtime sendiri, event, state machine, Safe Mode, dan lapisan verifikasi. Namun, ada sejumlah ketidakkonsistenan implementasi yang berpotensi membuat fitur terlihat berfungsi padahal hasilnya belum benar-benar terjamin. Referensi: [README repository](https://github.com/Fadhlijeu/deep-browser), [arsitektur](https://github.com/Fadhlijeu/deep-browser/blob/main/docs/ARCHITECTURE.md).

Catatan: ini audit statis terhadap kode yang tersedia di branch `main`. Gua belum menjalankan aplikasi, build, atau seluruh test suite dalam sesi ini. Jadi, temuan di bawah membedakan masalah yang terlihat langsung di kode dengan rekomendasi yang masih perlu diuji.

## 1. Prioritas tertinggi: perbaiki sistem agent

**P0 — Stop bisa menghasilkan status yang bertentangan**

Di [`extension/core/agent.js`](https://github.com/Fadhlijeu/deep-browser/blob/main/extension/core/agent.js), method `stop()` mengirim `TASK_CANCELLED` sekaligus `TASK_COMPLETED`.

Ini membuat UI, timeline, atau penyimpanan sesi berpotensi menganggap tugas yang dibatalkan sebagai tugas selesai.

**Perbaikan:** pembatalan harus memiliki satu terminal state yang otoritatif. Gunakan mekanisme pembatalan yang menghentikan operasi aktif, dan pastikan tidak ada aksi baru yang dijalankan setelah pembatalan diproses.

---

**P0 — Batas langkah agent tidak konsisten**

Dokumentasi constructor `Agent` menyebut default `maxSteps=25`, tetapi implementasi menggunakan `Infinity` saat nilainya tidak diberikan.

**Perbaikan:** gunakan batas langkah default yang eksplisit, batas waktu per tugas, anggaran pemanggilan model, dan anggaran percobaan ulang. Semua batas harus terlihat dan bisa dikonfigurasi.

---

**P0 — Status verifikasi belum selalu mencerminkan hasil nyata**

Di agent extension, `_verifyAction()` dapat mengembalikan `verified: true` untuk navigasi, klik, dan scroll hanya karena aksi melaporkan keberhasilan. Itu belum membuktikan tujuan aksi tercapai.

**Perbaikan:** gunakan bukti setelah aksi, misalnya URL tujuan, nilai field aktual, perubahan DOM yang relevan, status navigasi, atau hasil ekstraksi. Jika buktinya tidak cukup, statusnya harus `unverified` atau `outcome_unknown`, bukan otomatis sukses.

### Tutup loop agent secara konsisten

Gua menyarankan satu kontrak eksekusi yang berlaku untuk semua aksi:

Loop ini sebaiknya tidak mengandalkan teks dari model seperti “berhasil” atau status HTTP saja. Sistem harus mengamati browser lagi setelah tindakan, lalu menentukan apakah tujuan benar-benar tercapai.

Hal yang juga perlu diperiksa adalah penghentian ketika agent sedang menunggu respons LLM, approval, atau aksi browser. `stop()` tidak cukup hanya mengubah flag jika operasi yang sedang menunggu masih bisa melanjutkan eksekusi.

## 2. Arsitektur desktop dan extension masih perlu dirapikan

Ini salah satu masalah desain paling penting karena berpengaruh terhadap pemeliharaan seluruh proyek.

Saat ini terdapat dua arah implementasi:

- Desktop: Python `browser_use/` dan lapisan tambahan di `deep_browser/`.
- Extension: JavaScript/TypeScript di `extension/core/` dengan `Agent`, `BrowserSession`, `Tools`, `SecurityPolicy`, dan `StateMachine` sendiri.

Selain itu, [`sidepanelStore.ts`](https://github.com/Fadhlijeu/deep-browser/blob/main/extension/sidepanel-src/src/state/sidepanelStore.ts) masih memuat koneksi WebSocket ke `127.0.0.1:7788`, sementara [`service_worker.js`](https://github.com/Fadhlijeu/deep-browser/blob/main/extension/background/service_worker.js) menyatakan bahwa extension berjalan mandiri tanpa ketergantungan WebSocket/server.

Artinya, deklarasi arsitektur dan jalur implementasi belum sepenuhnya konsisten.

### Rekomendasi arsitektur

**Desktop runtime**

Electron → Browser Use Python → browser session desktop → provider LLM

Mengelola workspace, sesi desktop, browser yang dikelola aplikasi, dan orkestrasi native.

**Extension runtime**

SidePanel → extension agent → Edge active-tab adapter → provider LLM

Berjalan mandiri dan mengontrol tab aktif melalui API extension. Tidak bergantung pada daemon atau WebSocket desktop untuk menjalankan tugas.

---

**Kontrak bersama**

Schema aksi, event, state transition, kebijakan keamanan, aturan retry, serta format bukti verifikasi.

Kontrak dan tes perilaku dapat digunakan bersama tanpa mengharuskan kedua runtime memakai proses atau transport yang sama.

Ini sesuai dengan kebutuhan lu sebelumnya: extension dan desktop boleh memiliki proses eksekusi terpisah. Jangan membuat extension bergantung pada WS agar dapat berfungsi.

Satu catatan: karena Python `browser_use` tidak bisa langsung dijalankan di konteks JavaScript extension, jangan memaksakan klaim bahwa keduanya menggunakan satu runtime fisik. Pertahankan perilaku dan kontrak yang kompatibel, lalu uji masing-masing runtime secara mandiri.

Yang perlu dibersihkan:

- Hilangkan koneksi dan fallback daemon dari jalur extension mandiri jika memang tidak lagi dibutuhkan.
- Pisahkan jalur desktop dan extension supaya kegagalan salah satu tidak mengubah status atau eksekusi yang lain.
- Pastikan setiap sesi memiliki `runId`, `sessionId`, `tabId`, dan korelasi event yang jelas.
- Hindari implementasi state machine, approval, serta verifikasi yang berbeda perilaku antara desktop dan extension.
- Dokumentasikan mode yang benar-benar didukung, bukan hanya mode yang direncanakan.

## 3. Keamanan: Safe Mode harus menjadi penegak kebijakan, bukan sekadar UI

File [`security_policy.js`](https://github.com/Fadhlijeu/deep-browser/blob/main/extension/core/security_policy.js) dan [`safety.py`](https://github.com/Fadhlijeu/deep-browser/blob/main/deep_browser/policies/safety.py) sudah menunjukkan adanya konsep pemblokiran dan persetujuan manusia. Yang perlu diperkuat adalah konsistensi penerapannya pada setiap jalur eksekusi.

| Area             | Masalah atau risiko                                                                                     | Rekomendasi                                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Klasifikasi aksi | Pencocokan kata seperti `submit`, `delete`, atau `pay` tidak cukup untuk mengenali semua aksi berisiko. | Klasifikasikan berdasarkan jenis operasi, target, konteks, dan dampak.                                                          |
| Approval         | Tombol persetujuan UI bukan jaminan bahwa aksi yang dieksekusi sama dengan aksi yang disetujui.         | Ikat approval ke ID aksi, parameter, target, dan versi proposal; tolak jika berubah.                                            |
| Retry            | Aksi yang timeout belum tentu gagal; mungkin sudah diproses oleh situs.                                 | Baca ulang keadaan browser sebelum memutuskan untuk mengulang.                                                                  |
| Akses halaman    | Manifest extension meminta akses `<all_urls>` dan memasang content script pada seluruh URL yang cocok.  | Minimalkan host permissions dan gunakan akses per situs bila memungkinkan.                                                      |
| API key          | Kunci disimpan melalui `chrome.storage.local` dan digunakan oleh klien LLM extension.                   | Jelaskan model perlindungan kunci, jangan mencatatnya ke log, dan hindari menyimpan atau mengirim data halaman tanpa kebutuhan. |

### Perbaikan yang paling penting: `outcome_unknown`

Bayangkan agent menekan tombol “Submit”, lalu browser timeout. Ada tiga kemungkinan:

1. Formulir belum terkirim.
2. Formulir sudah terkirim, tetapi respons belum diterima.
3. Formulir terkirim sebagian atau situs menampilkan error setelah memprosesnya.

Agent tidak boleh langsung mengulang submit. Sistem harus memeriksa status halaman, notifikasi sukses, perubahan data, atau indikator lain yang relevan. Jika hasilnya tetap tidak diketahui, hentikan tindakan berisiko dan minta keputusan pengguna.

State machine extension sudah mengenal `outcome_unknown`, jadi konsepnya tidak perlu diciptakan ulang. Yang dibutuhkan adalah memastikan seluruh jalur eksekusi benar-benar mematuhi kontrak tersebut.

### Perbaikan keamanan tambahan

- Jangan mengizinkan aksi sensitif lolos hanya karena nama tool-nya tidak masuk daftar blokir.
- Gunakan default-deny untuk operasi yang tidak dikenal atau tidak terklasifikasi.
- Terapkan timeout dan masa kedaluwarsa approval.
- Batasi ukuran screenshot, isi DOM, dan data sensitif yang dikirim ke provider.
- Bedakan izin untuk membaca halaman, mengisi formulir, mengunggah file, mengirim pesan, dan menghapus data.
- Pastikan mode `Always Proceed` tidak menonaktifkan larangan absolut atau perlindungan atas aksi berisiko tinggi.

## 4. Lapisan verifikasi desktop perlu diperkuat

Di [`deep_browser/verification/engine.py`](https://github.com/Fadhlijeu/deep-browser/blob/main/deep_browser/verification/engine.py), `capture_state()` mencoba mengambil URL dan status dokumen. Namun, `dom_summary` masih berupa string kosong dan hash DOM yang dibuat berasal dari URL, status dokumen, serta string kosong tersebut.

Konsekuensinya, hash itu tidak benar-benar merepresentasikan perubahan DOM. Dua keadaan halaman yang URL dan status dokumennya sama akan menghasilkan hash yang sama, meskipun isi halaman telah berubah.

Selain itu, fallback verifikasi generik menganggap perubahan state sebagai verifikasi yang berhasil. Padahal, perubahan keadaan belum tentu berarti tujuan aksi tercapai.

Perbaikannya:

- **Navigation:** cocokkan URL aktual dengan tujuan, lalu periksa kesiapan halaman.
- **Click:** periksa efek yang relevan, bukan hanya perubahan fokus atau URL.
- **Input:** baca nilai field aktual dan bandingkan dengan nilai yang diharapkan.
- **Download:** pastikan file benar-benar terbentuk dan selesai ditulis.
- **Upload:** verifikasi bahwa situs menerima file, bukan sekadar file dipilih.
- **Form submission:** periksa indikator hasil di situs atau perubahan data yang dapat diamati.
- **Aksi generik:** gunakan status `executed` atau `unverified` jika bukti belum cukup.

Hindari menjadikan hash seluruh DOM sebagai satu-satunya ukuran keberhasilan. Lebih baik memverifikasi kondisi spesifik yang relevan dengan aksi tersebut.

## 5. Optimasi performa dan konsumsi token

Karena Deep-Browser menggunakan LLM sekaligus browser sungguhan, waktu dan biaya dapat membengkak apabila setiap langkah mengirim seluruh DOM serta screenshot berukuran besar.

**DOM observation yang selektif**

Ambil elemen interaktif yang relevan, nama aksesibilitas, konteks lokal, dan indeks stabil. Hindari mengirim seluruh struktur halaman pada setiap langkah tanpa batas.

---

**Screenshot sesuai kebutuhan**

Gunakan screenshot saat tugas memerlukan pemahaman visual, posisi koordinat, atau verifikasi visual. Untuk aksi DOM yang sederhana, jangan mengambil screenshot penuh jika tidak dibutuhkan.

---

**State diff, bukan pengulangan penuh**

Bandingkan URL, tab aktif, elemen terkait, nilai field, dan perubahan halaman. Kirim hanya perubahan yang berguna untuk keputusan berikutnya.

---

**Timeout, retry, dan anggaran**

Tambahkan timeout per request, batas total tugas, penanganan HTTP 429/5xx, backoff dengan jitter, serta pembatalan yang benar-benar menghentikan pekerjaan.

Di [`llm_client.js`](https://github.com/Fadhlijeu/deep-browser/blob/main/extension/core/llm_client.js), `_fetchWithRetry()` sudah mencoba ulang ketika terjadi kegagalan jaringan, tetapi perlu ditinjau agar timeout, pembatalan, dan respons HTTP sementara ditangani secara konsisten. Jangan mengulang aksi browser hanya karena request LLM gagal.

### Perbaikan penting untuk indeks elemen DOM

Indeks elemen yang dipakai agent juga perlu memiliki aturan masa berlaku. Setelah navigasi atau perubahan DOM besar, indeks lama bisa menunjuk ke elemen yang berbeda.

Gua menyarankan setiap observasi memiliki `observationId` atau versi DOM. Aksi harus merujuk ke versi observasi yang benar; bila sudah kedaluwarsa, agent wajib melakukan observasi ulang sebelum bertindak.

Ini lebih aman daripada mengandalkan indeks numerik yang tetap dianggap valid setelah halaman berubah.

## 6. UI extension: minimal, konsisten, dan fokus pada tugas

Dari struktur kode, extension sudah memiliki komponen `SlimHeader`, `AssistantThread`, `ToolStepCard`, `HitlApprovalCard`, `LogsView`, serta modal untuk pengaturan. Jadi, menurut gua, lu tidak perlu merombak seluruh komponen dari nol.

Yang lebih penting adalah memperbaiki hierarki informasi dan state UI supaya tampilannya sekaligus mencerminkan keadaan agent dengan akurat.

**A. Chat sebagai tampilan utama**

- Header ringkas berisi identitas, status agent, dan kontrol tugas.
- Input prompt selalu mudah ditemukan di bagian bawah.
- Model, execution mode, dan preset berada dalam kontrol sekunder yang ringkas.
- Jangan menjadikan seluruh topbar sebagai sidebar; gunakan sidebar hanya untuk riwayat sesi atau navigasi yang memang memerlukan ruang.

---

**B. Timeline tindakan yang jelas**

Tampilkan aksi yang sedang berjalan, targetnya, hasil verifikasi, durasi, dan error yang relevan. Detail reasoning atau metadata teknis dapat disembunyikan dalam bagian yang bisa dibuka.

---

**C. Approval yang tidak ambigu**

Tampilkan tindakan yang akan dilakukan, target situs, konsekuensi, dan tombol yang jelas untuk menyetujui atau menolak. Setelah keputusan dikirim, jangan menampilkan approval yang sama sebagai masih menunggu.

### Hal konkret yang perlu diperbaiki di UI saat ini

1. **Tipografi:** [`assistant-theme.css`](https://github.com/Fadhlijeu/deep-browser/blob/main/extension/sidepanel-src/src/styles/assistant-theme.css) mendefinisikan `--font-serif` dengan Times New Roman, tetapi `html, body, #root` masih menggunakan `var(--font-sans)`. Jika arah visual lu tetap Times New Roman, variabelnya harus benar-benar digunakan pada area yang dimaksud.
2. **Status:** jangan menyamakan `standalone`, `connected`, `running`, dan `completed`. Status koneksi dan status tugas merupakan dua hal berbeda.
3. **Animasi:** transisi panel, perubahan status, tool card, dan approval perlu memiliki durasi serta easing konsisten. Hormati `prefers-reduced-motion`.
4. **Kerapian CSS:** ada deklarasi `.status-pill` yang berulang. Audit selector duplikat dan style lama sebelum menambahkan lebih banyak override.
5. **Komponen ganda:** repository memiliki `sidepanel-src`, hasil build `sidepanel/dist`, dan implementasi lama di `sidepanel/`. Pastikan hanya satu sumber menjadi acuan UI, dan build selalu menghasilkan artefak dari source terbaru.
6. **Error UX:** kegagalan API, tab tertutup, izin ditolak, timeout, dan hasil yang belum diketahui harus mempunyai tampilan pemulihan yang berbeda. Jangan hanya menampilkan toast generik.

Untuk animasi, targetnya bukan membuat semua komponen bergerak. Prioritaskan transisi yang memberikan informasi tentang perubahan state, bukan dekorasi.

## 7. Pengujian: banyaknya test belum cukup

Repository memiliki test desktop, test extension, test Python, dan beberapa test integrasi. Itu fondasi yang bagus. Namun, gua belum menjalankan test tersebut, jadi jumlah file test tidak boleh dianggap sebagai bukti bahwa semua jalur bekerja.

Yang gua prioritaskan adalah satu rangkaian pengujian end-to-end yang mencakup kasus nyata berikut.

| Skenario                         | Hasil yang wajib dibuktikan                                                    |
| -------------------------------- | ------------------------------------------------------------------------------ |
| Tugas sederhana                  | Agent membuka halaman, membaca informasi, lalu memberikan jawaban yang sesuai. |
| Klik gagal                       | Agent mendeteksi bahwa target tidak berubah dan tidak mengklaim sukses.        |
| Navigasi lambat                  | Agent menunggu dengan batas waktu yang tepat, bukan melakukan aksi prematur.   |
| Stop ketika LLM sedang merespons | Tidak ada aksi baru setelah pembatalan.                                        |
| Approval ditolak                 | Aksi sensitif tidak dieksekusi.                                                |
| Approval kedaluwarsa             | Eksekusi berhenti dan UI menjelaskan alasannya.                                |
| Timeout saat submit              | Agent memeriksa hasil sebelum mencoba ulang.                                   |
| Tab ditutup                      | Tugas berakhir dengan status yang benar dan resource dibersihkan.              |
| Dua sesi berjalan bersamaan      | Tidak terjadi kebocoran state, event, atau browser profile.                    |
| Provider gagal                   | Retry, error, dan pembatalan ditangani tanpa duplikasi aksi.                   |

Tambahkan pula pengujian visual untuk extension pada beberapa lebar SidePanel. Ini penting karena layout yang bagus di jendela lebar bisa rusak ketika panel menyempit.

### Gate CI yang gua sarankan

- Typecheck dan lint desktop.
- Build extension dari `sidepanel-src`.
- Unit test untuk state machine, kebijakan keamanan, adapter browser, dan parsing respons LLM.
- Test integrasi Python dan extension.
- End-to-end dengan fixture website lokal yang deterministik.
- Live test Gemini yang opsional dan hanya berjalan ketika API key tersedia.
- Visual regression untuk layar utama, timeline, error, dan approval.

Pisahkan test yang membutuhkan jaringan atau API berbayar dari test reguler. Dengan begitu, hasil CI tetap dapat direproduksi tanpa bergantung pada provider eksternal.

## 8. Urutan pengerjaan yang paling efektif

Gua tidak menyarankan agent coding langsung mengerjakan semua poin di atas sekaligus. Dengan ukuran repository ini, perubahan UI, runtime, dan sistem agent secara bersamaan berisiko membuat regresi baru.

Urutannya sebaiknya seperti ini:

1. **Stabilkan agent dan state machine**

   Perbaiki `stop()`, batas langkah, pembatalan, terminal state, dan status `outcome_unknown`. Buat test regresi untuk setiap kasus.

2. **Tegaskan batas runtime**

   Pisahkan jalur desktop dan extension sesuai kebutuhan. Hilangkan ketergantungan WebSocket dari jalur extension mandiri, tanpa merusak kemampuan desktop.

3. **Perkuat verifikasi dan Safe Mode**

   Verifikasi hasil aktual, ikat approval pada aksi yang disetujui, serta pastikan aksi berisiko tidak dapat melewati policy gate.

4. **Optimalkan observasi dan LLM**

   Kurangi DOM dan screenshot yang tidak perlu, tambahkan timeout dan anggaran tugas, serta perbaiki strategi retry dan recovery.

5. **Rapikan UI extension**

   Pertahankan komponen yang masih layak, konsolidasikan sumber UI, lalu sempurnakan tipografi, animasi, timeline, dan error state.

6. **Validasi end-to-end**

   Jalankan semua gate CI, uji browser sungguhan, dan pastikan fitur desktop serta extension bekerja sesuai kontraknya.

## Kesimpulan gua

Deep-Browser tidak perlu ditulis ulang dari nol. Struktur yang sudah ada cukup kaya untuk dikembangkan lebih lanjut. Yang dibutuhkan adalah memastikan bahwa komponen-komponennya benar-benar bekerja sebagai satu produk yang konsisten, bukan sekadar banyak modul dengan nama dan tanggung jawab yang terlihat benar.

Tiga hal yang paling penting:

- **Agent tidak boleh mengklaim sukses tanpa bukti.**
- **Extension harus tetap mandiri jika itu merupakan persyaratan arsitektur lu.**
- **Setiap perbaikan harus dibuktikan lewat test dan perilaku browser nyata.**

Kalau lu mau mengirim instruksi ke Antigravity, gua menyarankan memulai dari audit dan perbaikan P0 di atas, dengan larangan menulis ulang proyek atau menghapus fitur yang sudah ada. Setelah fondasi stabil, barulah UI dan optimasi lanjutan dikerjakan.
